> [Question] Тяжёлый экран/лента тормозит: разверни дерево гипотез (лишние ре-рендеры, бандл, main thread, память), что мерил и что реально помогло?

Дерево гипотез:
1. Ре-рендеры - React.memo + Profiler, нашли лишние вызовы
2. Бандл - Долго грузит, code-split по роутам, vendor-chunk, скортатили на ~30%
3. Main thread - long tasks, вынесли тяжёлые вычисления в Web Worker и разбили long tasks на async tasks
4. Память - утечки в listener'ах/таймерах, пофиксили в cleanup

Реально помогло: мемоизация + async + bundle как правильно в основном является решением.

Мерил:
- длительность фреймов, long tasks, recalc styles, layout
- В React DevTools Profiler, длительность коммитов, кол-во рендеров компонента, flamegraph
- Lighthouse, TBT, LCP
- memory heap до/после навигации
- размер чанков, tree-shaking holes
- и в ручную для каждого statement с помощью небольшого бечмарка или просто performance.now()
Крупный клиент с тяжёлым состоянием: как держал модель данных и рендер целиком, где разваливалось, как чинил?
- Использовал Redux, React Context и глобал стейт (где уместно)
- Не использовал Thunk, потому что состояния приложения (бизнес) и API я разделил (Tanstack Query), и получилось поддерживать тяжёлые состояния с лёгкостью.
- Хорошо описанные интерфейсы состояний
- Локализация стейта - Там где можно, состояния не должны покидать компоненты, там где нужно передать состояние на несколько компонентов вниз по дереву, я мог использовать React Context API, а если компонентов очень много в разных местах или Бизнес стейт, то тогда уже Redux. Если это например курс валют или юзер, то его можно в глобал стейт.
- Хорошая модулярность - помогает не запутаться со сложными состояниями
- Убедиться что изменение состояние происходит только в заранее известных функциях чтобы изменять было проще

Особо ничего не ломается если следовать таким правилам
